## 1. 问题与目标

**现状**（D23/D24 后）："照老规矩处理"能被规则/embedding 检测为 history-content 指代，
但解析路径只有一条——绑定到某个历史会话（D4 两波绑定：先消歧 history-event，再读该
会话 diff）。两个缺口：

1. **惯例 ≠ 会话**。用户说"照旧"时常指"我们一贯的做法"，不是"上次那个会话"。绑到
   单次会话会把惯例窄化为一个快照（上次恰好没做错误处理时，注入就是错的）。
2. **无会话可绑**。新机器、清理过会话、或惯例早已沉淀为习惯（无对应近期会话）时，
   现路径诚实 not-found——而用户明明有明确的"老规矩"。

**目标**：会话结束时由**宿主 LLM** 把会话中反复出现的工作惯例蒸馏为结构化条目，存入
memory.json（schema v2 新增 `conventions` 段）；解析时，"照旧 / 老规矩 / 按咱们那套"
类指代**优先**命中本项目惯例，注入惯例值并注明出处；无惯例或未达命中门槛时，回退
现有会话绑定路径（行为不劣化）。

**非目标（明确不做）**：

- 不做跨项目全局惯例（惯例严格按 `projectKey` 隔离，同 D24 先验的项目隔离语义）；
- 不做云同步 / 云存储（本地文件即全部状态，复制文件即迁移，同 D24）；
- 不做词条自动学习（个人惯用语词典维持显式注册，D24.4 的错学成本论证不变）；
- 不做惯例的自动负面学习（用户否定某惯例后自动删除——v0 只提供显式纠正路径，见 §8）。

## 2. 总体数据流

```
会话结束（宿主事件）
   │
   ▼
宿主适配器组装总结提示词（§4 草案）＋ 会话素材（用户话语 + 关键决策摘录）
   │
   ▼
宿主 LLM 离线总结（headless 调用，不阻塞用户；失败即放弃本次蒸馏）
   │  产出：结构化惯例数组（严格 JSON；宁缺毋滥）
   ▼
适配器校验（形状/上限/敏感内容防线）→ core MemoryStore.addConvention() 落盘
   │  memory.json（schema v2，conventions 段，原子写、写时裁剪）
   ▼
下次解析：检测器照常检出「照旧/老规矩」类 history-content 指代
   │
   ▼
引擎解析：本项目惯例优先（§6 语义）→ 命中 → 注入「惯例：<表述> = <内容>」
   （display 注明 生成于 <依据会话>）＋ 首次使用经 L1 授权（§7）
   │ 未命中 / 未授权 / 有歧义
   ▼
回退现有路径：会话绑定（D4 两波）→ 仍无 → 诚实 not-found（原样透传）
```

**纪律不变量**：core 只做存取与确定性解析（零 LLM，R4/依赖红线不破）；蒸馏只发生在
宿主事件里、由宿主模型执行；惯例**只在用户说出口的指代被检出后**才注入（预测注入
红线）；任何一环失败 → 行为等同今天（fail-open）。

## 3. 蒸馏执行者与宿主事件（事实表）

| 宿主 | 会话结束事件 | 事实来源 | 宿主 LLM 调用形态 |
|---|---|---|---|
| pi | `session_shutdown`（`event.reason: quit/reload/new/resume/fork`） | `.supervision/pi-extensions.md`（锁定版 0.85.1 扩展文档） | 子进程 `pi --offline --no-session -p "<提示词>"`（README 已验证的 headless 形态） |
| Claude Code | hooks `SessionEnd` | 官方 hooks reference（2026-09-14 核实入口；载荷细节实现时核实） | 子进程 `claude -p "<提示词>"`（headless print 模式） |
| OpenCode | `event` hook 的 `session.idle`（Event 判别子，`@opencode-ai/sdk` types.gen） | 锁定版 `@opencode-ai/plugin@1.18.30` → SDK 类型声明 | SDK client 的 prompt 调用面（实现时核实）；备选：仅标记待蒸馏，下次 `chat.message` 补做 |

注意事项：

- 三处 headless 调用都是**进程外、异步、非阻塞**的：蒸馏失败/超时只损失本次蒸馏，
  绝不影响宿主会话本身；启动即忘（fire-and-forget）+ 自身超时（建议 60s 上限）。
- 蒸馏输入是**当前会话素材**（用户话语与决策摘录，由适配器从宿主会话 API 取，不重读
  全量 transcript——沿用各适配器"只用官方可核实字段"的纪律）。
- **决策点 D-A**：蒸馏时机。备选：①会话结束即蒸馏（本文推荐：素材最新鲜，跨宿主
  立即可用）；②惰性蒸馏（下次用户说出"照旧"且无惯例时，现场蒸馏：省算力但首次
  延迟高、且"没说出口就别动"的红线更难守）；③混合（结束时蒸馏 + 命中失败时补蒸馏）。
  推荐①起步，②③留评审。

## 4. 宿主总结提示词（草案）

以下为适配器组装时的模板（`{{SESSION_EXCERPT}}` 为会话素材、`{{PROJECT_KEY}}` 为项目
路径、`{{EXISTING}}` 为本项目现有惯例表述列表，供模型做增量/冲突判断）：

```
你在为编码助手「潜意识引擎」做会话惯例蒸馏。请阅读下面这段会话记录，找出其中
【反复出现、明确成型的项目工作惯例】（如错误处理方式、命名风格、提交信息格式、
目录组织、测试约定），输出 JSON。

规则：
1. 宁缺毋滥：只有当会话中有明确证据（用户明确要求过、或双方确认过且被执行）时才
   输出；单次出现、猜测的、用户否决过的做法，一律不输出；
2. 不蒸馏敏感内容（凭据、私人文本、与工作惯例无关的个人信息）；
3. 每条惯例：expression=惯例名（≤16 字，领域名词，如「错误处理」「提交信息」），
   content=惯例内容（≤120 字，可执行的具体描述，如「统一 try/catch 包裹并 log
   错误，不吞异常」）；
4. 与现有惯例（{{EXISTING}}，可能为空）同名的：若本会话做法与之冲突，输出新版本
   （后写胜）；一致则不重复输出；
5. 只输出 JSON 数组，无其他文本：[{"expression":"...","content":"..."}]，最多 5 条。

项目：{{PROJECT_KEY}}
现有惯例：{{EXISTING}}
会话记录：
{{SESSION_EXCERPT}}
```

适配器侧校验（不信模型输出，同 memory.json 手工编辑的不可信输入纪律）：JSON 解析
失败 → 放弃；条目逐条 `isConvention` 形状校验（§5）→ 非法丢弃；超 5 条截断；
`expression`/`content` 须通过敏感内容粗筛（正则：凭据形态 token、长随机串）→ 命中
即丢弃该条并记 warn。

**决策点 D-B**：提示词与判定门槛属于"调参面"，建议实现时进入 `.supervision/` 评估
（蒸馏质量用人工标注小集，同 embedding 评估纪律），不在此预置阈值。

## 5. memory schema v2（conventions 段）

```json
{
  "version": 2,
  "disambiguation": [ /* 同 v1 */ ],
  "phrases": [ /* 同 v1 */ ],
  "conventions": [
    {
      "id": "c-1742310400-8f3a",
      "projectKey": "/work/proj",
      "expression": "错误处理",
      "content": "统一 try/catch 包裹并 log 错误，不吞异常",
      "basedOnSessionId": "abc123",
      "basedOnTitle": "错误处理改造",
      "generatedAt": "2026-09-15T10:00:00.000Z",
      "lastHitAt": "2026-09-18T09:00:00.000Z",
      "hitCount": 3
    }
  ]
}
```

字段与任务书映射：id、projectKey（项目）、expression（表述）、content（内容）、
basedOnSessionId/basedOnTitle（依据会话）、generatedAt（生成时间）；lastHitAt/hitCount
服务衰减与排序（§7），由引擎解析命中时回写。

- **上限与裁剪**（写时执行，同 D24 纪律）：每项目 ≤ 20 条（超限按 lastHitAt 最旧
  淘汰）；全局 ≤ 200 条；expression ≤ 16 字、content ≤ 120 字（与提示词一致）。
- **迁移**：`parseMemoryData` 接受 version 1（conventions 视为空）与 version 2；
  写路径恒写 v2。旧版 core 读 v2 文件 → 校验失败 → fail-open 空记忆（降级安全）。
  `exportMemory`/`importMemory` 同步支持 v2；复制文件即迁移（不变）。
- **core API 增量**：`isConvention(v)`、`parseMemoryData` v2、`MemoryStore`
  `listConventions(projectKey)` / `addConvention(entry)`（File/InMemory 双实现 +
  写时裁剪）、引擎解析侧惯例命中（§6）。core 仍是零依赖、零 LLM。

## 6. 解析侧语义（红线承接）

检测层**零改动**：D23 的"照旧 / 老规矩 / 那套"模板照常产出 history-content 指代。
惯例是**解析侧**的一级候选，与消歧先验同级（引擎内确定性逻辑，不是新数据源）：

1. **锚定要求（不猜测）**：命中惯例必须有一个锚——
   a. **域锚**：指代周边文本与某惯例 expression 匹配（精确包含，或 embedding 臂
      复用现有近邻分类）——"照旧处理**错误**"→ expression「错误处理」；
   b. **唯一锚**：裸"照老规矩来"（无域锚）且本项目**恰有一条**活跃惯例 → 唯一即命中；
   c. 多条活跃惯例且无域锚 → **不静默注入**：按现有降级矩阵把惯例列表作为候选
      （pi 弹 select；claude/opencode 注入「待确认」块让模型问用户）。
2. **优先序**：惯例命中优先于会话绑定（惯例是跨会话沉淀，语义上更强）；惯例未命中
   才走 D4 两波会话绑定；都无 → not-found 原样透传。
3. **注入形态**：`惯例：错误处理 = 统一 try/catch 包裹并 log 错误，不吞异常
   （惯例·生成于「错误处理改造」会话 · 已用 3 次）`——与 core 组装器的
   `（来源：recent-sessions）` 标注同风格；resolvedRefs 的 display 同样带
   `（惯例·生成于 <标题>）`后缀（透明性，同先验代选的`（按你的常用选择）`先例）。
4. **红线测试锁定**（实现验收必测）：无指代零开销透传不变；惯例绝不进入用户没提
   "照旧/老规矩"的 prompt（预测注入）；跨项目不串扰；display 必带生成出处。

## 7. 安全模型：蒸馏物按 L1 对待（决策建议）

DESIGN §8 分级里，同源数据 session-content 是 L0（用户以"上次那个会话"显式指名）。
惯例与之差两级证据：**内容由 LLM 蒸馏生成**（有错蒸馏风险）+ **注入进新会话时用户
并未指名任何具体会话**（证据链长于先验——先验至少只排序既有候选）。建议：

- **首次注入前需一次授权**（L1-grant-once 语义）：pi 弹 confirm（"按惯例
  「错误处理」= … 注入？以后本项目自动使用，可随时撤销"）；claude/opencode 无确认
  通道 → 不注入确定结论，注入「待确认」块（含惯例内容与出处）让模型转问用户；
  授权落 grants.json（sourceId `conventions`、scope 按项目），撤销 = 删该条授权。
- 授权后的后续注入不再打扰（L1 的"授权一次"），但 display 溯源标注恒在。
- **决策点 D-C**：备选 ①L0（与 session-content 同级：注入即用，只靠 display 审计）；
  ②**L1-grant-once（推荐，理由如上）**；③L2（每次确认——过于打扰，惯例的意义就在
  免重复确认）。蒸馏**写入**本身不需要授权（本地文件、可删可改、不注入就不外显），
  但**注入**需要。
- **决策点 D-D**：错误蒸馏的纠正路径。备选：①仅手工编辑 memory.json（删/改该条，
  v0 最小）；②display 附惯例 id，宿主提供"撤销此惯例"命令（pi command /
  claude slash command 形态，工作量 +1 天）；③用户话语否定（"这次别按老规矩"）
  → 识别为该次不用但不删惯例。推荐 ①+③ 起步（③只是解析期常规路径：指代被
  否定语覆盖时不注入），②留评审。

**衰减 / 冲突策略**（写时统一执行，读侧无状态）：

- **衰减**：`lastHitAt` 距今 > 90 天 → 写时淘汰（"老规矩"三个月没用即视为过期，
  与先验 14 天窗口同理但周期更长——惯例的半衰期长于选择习惯）；hitCount 仅作
  display 与淘汰排序参考，不作命中门槛（避免"常用即永久"的自增强）。
- **冲突**：同项目同 expression 新旧并存 → **后写胜**（新蒸馏反映当前偏好），旧条
  整条替换（id、basedOn、generatedAt 一并更新，不留双活）；不同 expression 各自
  独立。淘汰/替换都在写时发生，读侧永远只见确定的单条。
- **蒸馏自增强防线**：提示词把 {{EXISTING}} 交给模型是为"同名冲突时输出新版本"，
  不是"把现有惯例复述一遍"——规则 4 已要求一致则不重复输出；适配器对与现有条目
  逐字节相同的输出直接丢弃（不刷新 generatedAt，防止"洗时间"绕过衰减）。

## 8. 透明性与审计汇总

| 环节 | 透明性手段 |
|---|---|
| 蒸馏落盘 | memory.json 人可读（两空格缩进），条目带依据会话与时间 |

| 禁用 | 清空 conventions 数组，或删 memory.json（行为回到 v1/无记忆） |

## 11. 实现验收标准（供后续里程碑）

1. "照旧处理错误"注入惯例值且 display 带出处；无惯例时行为与今天逐字节一致；
2. 裸"照旧"多惯例 → 候选/待确认，绝不静默注入；跨项目不串扰；
3. 蒸馏失败/超时/输出非法 → 会话与宿主零影响（fail-open 测试锁定）；
4. 首次注入经授权（pi confirm / 无通道宿主待确认），grants 可撤销；
5. 90 天未命中写时淘汰、同名后写胜、相同输出不洗时间（测试锁定）；
6. core 仍零依赖零 LLM；check / check-deps 全绿（无需新增 R 规则——不新增任何
   运行时依赖）。
